# Phase 1c / B3 音量エンベロープの点数制限

> 開発時点の記録です。2.2.84の最新の採否・制約・公開状態は[リリース報告](PVE-2.2.84-RELEASE-REPORT.md)を参照してください。


2026-10-23。実装前の方式判断（結果は検証後に追記）。未公開・バージョン更新なし。

## 方式判断

| 方式 | 評価 |
|---|---|
| A：256点を維持し超過編集を拒否 | 情報は守れるが、境界を1点足すだけのsplit/trimを拒否し、連動音声・ドラッグなどの部分変更を広く巻き戻す必要がある。編集作業を妨げるため不採用 |
| B：上限を引き上げる | 採用。手動ポイント追加の目安を1024点に引き上げ、normalize/split/trim/保存復元には切捨て上限を置かない。内部の境界追加が1024点を超えても保持する。手動追加の超過だけは変更・履歴作成前に拒否して理由を表示 |
| C：意味を保持する簡略化 | 同じ値の点でもholdランプ幅・微小な境界に意味がある。誤差なしの保証と追加操作の予測性を優先し、今回は自動簡略化しない |

既存データの移行・削除はしない。B2の任意属性と評価式を維持する。旧版で256点超のデータを再保存すると失われ得るため、旧版へ戻す前には別名バックアップが必要。Mac出力側の切捨ても撤去し、長い式による深さ・コマンド引数制限に対処する。処理の大規模変更ではなく、同じ区間式の条件分岐配置と受渡しだけを必要最小限変更する。

## 原因と修正

**確認した事実**：`normalizeEnvelope`の先頭256点切出しと`addEnvelopePoint`の追加後切出しで、末端や新規点が黙って失われていた。Macの`gain_envelope_expression`にも先頭256点制限があった。旧256点のtrim終了は1秒に対して0.992217898833秒、split終了は0.999秒に対して0.996108949416秒。先頭・途中への追加では元の末端IDが消え、末端への追加では追加点自体が消えた。修正前の記録（開発監査資料・配布対象外）。

| ファイル / 関数 | 今回の変更 |
|---|---|
| `dist/clip-envelope.js` / normalizeEnvelope・addEnvelopePoint | 正規化の切捨てを廃止。手動新規追加のみ1024点で入力不変の例外。既存点更新は超過後も可能。splitEnvelope・trimEnvelopeのB2評価式は変更せず、追加した境界を全保持 |
| `dist/clip-envelope-ui.js` / materialize・doubleClick・point drag | 仮想端点は手動予算を消費せず保持。拒否はonBegin/履歴作成前。1023点＋手動1点＋両端点＝1026点も保持。密集点の固定1ms移動余白で隣点を越えないよう、現在の間隔から余白を制限 |
| `dist/app.js` / envelope-set・onLimit | インスペクターも更新・checkpoint前に追加可否を判定。理由を表示。B1部分は変更なし |
| `engine/core.py` / gain_envelope_expression | 切捨てを廃止。32点超は同じ区間式を平衡二分木へ配置し、FFmpegの式の入れ子深度制限を回避 |
| `engine/audio_engine.py` / render_tracks | 32KB超の同じフィルター文字列を使い捨てファイル経由で渡す。成功・失敗ともfinallyで削除 |

データ属性や保存形式は追加していない。`holdRampSeconds`、`editBoundary`、元のランプ開始位置は保持する。事前コンパイルと再生scheduler本体はhash不変。音声評価・Speed・B4・レンダラーは変更していない。FFmpegのファイル引数には実在する[`-/filter:a`構文](https://www.ffmpeg.org/ffmpeg.html)を使用し、原子的置換などは前提にしていない。

## 境界・編集テスト

| 入力点数 | normalize | trimで両端を追加 | 末端後でsplitした左側 | 手動新規追加 |
|---|---:|---:|---:|---|
| 254 | 254 | 256 | 255 | 保持 |
| 255 | 255 | 257 | 256 | 保持 |
| 256 | 256 | 258 | 257 | 保持 |
| 257 | 257 | 259 | 258 | 保持 |
| 1023 | 1023 | 1025 | 1024 | 保持 |
| 1024 / 1025 | 全保持 | 1026 / 1027 | 1025 / 1026 | 変更前に拒否 |

全ケースで先頭・途中・末端追加、元ID保持、既存点更新・削除、JSON→sanitize復元を検証。split/trimの開始0と終了時刻は、実際に関数へ渡した区間長に厳密一致する。4msクリップ、holdランプ途中のsplit、1ps境界、8回trim、連動音声のsplitも確認。短い区間では従来の操作可能長の制約を変更していない。

Chrome 155 / WebKit 26.5の実画面で257点のsplit、trim、Undo/Redo、`.project`ダウンロード→ファイル選択復元を確認。1024点での拒否はproject全文とUndoの可否が不変で、説明表示あり。同じ点数でも既存点更新・削除・削除Undoは成功。密集点のドラッグ順序と上限拒否時のonBegin/commit/set呼出ゼロは実gesture handlerで検証した。

## 数値・PCM・B2回帰

- B3：287,631時刻を元素材座標で比較。最大 **1.0302869668521453e-13 dB**（反復trim、元0.738291600452416秒、編集後0.681212790884416秒）。事前基準1e-8 dBを変更していない。
- JS実`mixWindow/gainAtCompiled`、254〜1026点の7条件×96,000サンプル：修正後PCM差 **0**。旧実装の最大差は257点で0.0155212、1024点で0.1692223。既存のclip declickを除いてエンベロープだけ比較した。
- 実OfflineAudioContext：1024点、Chrome/WebKit各4,800サンプル、同じscheduler条件の参照とPCM差 **0**（基準1e-7）。
- 実FFmpeg 8.0.1：7点数条件の元曲線・split左右・trimをサンプル評価と本番64サンプル評価で比較。最大PCM差 **4.470348358154297e-8**（基準2e-7）。未編集曲線とJSの比較は9桁時刻文字列丸めとfloat32変換を含み、最大4.408454801208e-8（1024点、元0.942375秒）。
- Macと同じ`render_tracks`を1026点で実行し、ステレオ96,000サンプル出力、末尾の有効音、長い式のファイル渡しを確認。実行失敗注入でも一時filterを削除し、入力projectは不変。
- B2既存数値・微小境界・連動テスト成功。FFmpeg **264ケース / 6,227,896サンプル、PCM差0、旧78式の文字列一致**。holdランプの意味は変更なし。既存8ms declickと64サンプル評価位相により、分割後の生PCMと未分割生PCMの完全一致は引き続き保証しない。

## 未検証事項と判断

**未検証**：実機iPhone/Safari、実聴、長時間・多数クリップでの負荷、1027点を大幅に超えるデータ、FFmpeg8以外、MacアプリZIP/HTTP全体と映像付き全出力。ブラウザは実音声DSPまで、Macは実FFmpeg音声書き出しまでで、映像の納品品質を今回保証したわけではない。構造編集の点数切捨ては撤去したが、無限のデータ量を処理できるという意味ではない。

正規化の既存同時刻/通常1us近接点統合、手動追加の既存0.1ms近接点更新規則は別仕様として維持。B2の`editBoundary`による微小間隔保持は回帰検証済み。旧版へ戻す場合は別名バックアップを用意し、256点超を旧版で上書き保存しない。

**B3は採用推奨、B4へ移行可能**。公開・バージョン更新は未実施。今回の音声検証を正式公開の全体受入の代用にはしない。
