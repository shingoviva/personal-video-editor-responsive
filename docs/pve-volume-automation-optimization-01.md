## 2. 事前調査と採用アルゴリズム

旧`gainAt()`は、1サンプルごとにキーフレームの無効値除去、数値化、clamp、安定ソート、補間を行っていました。`scheduleGain()`は最大0.15秒×48kHz＝7,200サンプルのFloat32カーブを生成します。そのため同じ配列に対するfilter/map/sortを、1カーブ内で7,200回繰り返していました。

変更後は**1カーブの生成中に限り**ソート済みポイントを使い回します。サンプル数、時刻式`local + span*i/(count-1)`、乗算順、fadeとdeclick、Float32への格納は同じです。重複時刻の点を統合せず、区間探索も従来の順序のままにしました。`envelopeGainAt()`の二分探索・dB変換・hold直前5msのランプも変更していません。

### 配列・確保量

通常のArrayと有効キー3点の場合、満量の1カーブについてのソース上の個数です。ヒープ実測やGC停止時間の測定ではありません。

| 項目 | 変更前 | 変更後 |
|---|---:|---:|
| filterの返す配列 | 7,200 | 1 |
| mapの返す配列 | 7,200 | 1 |
| sort呼出 | 7,200 | 1 |
| mapが生成するポイントobject | 21,600 | 3 |
| Float32Array本数 | 1 | 1 |
| Float32データ領域 | 28,800 bytes | 28,800 bytes |

sort自体はその配列を整列するため、sortの返値を「別の配列1本」とは数えていません。内部作業領域、objectヘッダ、JIT/GCによる実確保量は未測定です。キー0個でも旧実装のfilter/mapは配列を返します。短い末尾区間や停止時のサンプル数は従来通りです。

### 予約と無効化

`gainKey=JSON.stringify([c.audio,trackVolume,duration])`、clockとの30ms差、`until-40ms`による再予約条件、`cancelScheduledValues()`→`setValueCurveAtTime()`または`setValueAtTime()`は変更していません。停止時の`gainKey=null`も維持しています。

新たな永続キャッシュは設けません。再生成のたびに最新のキーをコンパイルするため、インプレース編集、Undo/Redo、素材変更、尺変更、キーフレーム変更、プロジェクト読み込みで古い整列結果を参照する経路がありません。Float32Arrayを複数の予約間で共有・上書きする最適化も行っていません。

### 診断負荷と同期の限界

同じdetailed設定での比較であり、通常モードのCPU削減率ではありません。計時粒度・hook・GPU timerの影響は残ります。今回OFF/ONの対照を再測定しておらず、既存baselineの対照でも診断overheadをノイズから明確には分離できませんでした。「診断負荷ゼロ」とは扱いません。

同期指標は動画のsource位置と基準clockの差です。符号付き平均/p95であり、絶対誤差p95やスピーカーからの音声遅延ではありません。Fの符号付き平均は前後の範囲が重なり、Gも範囲が重なるため改善・悪化は判断しません。clock、gate、seek経路と予約時刻は不変です。物理的な音声・映像同期は実機の聴視確認が必要です。

## 4. 数値・音声一致

- Nodeの旧式との比較：**188,584件、最大絶対誤差0**。
- キーなし／単一点／複数点／同時刻／負時刻や無効値の除去／境界／極短尺・長さ0／急変／fade重複／hold／seek／停止再開／レーン音量／編集・Undo/Redo相当・JSON再読み込みを検証。
- 108パターンを含む予約操作列について、旧式と新式のFloat32カーブ、cancel/value/curveの時刻と長さを完全一致で検証。7,200点のカーブでコンパイルが1回、省略tickで0回、編集直後に再生成されることも確認。
- Chrome、Playwright WebKitの両方で、7レーン×ステレオ、開始時刻0／1.997／7.8秒、48kHzのOfflineAudioContextを使用。renderを途中でsuspendし、実際の進行時刻で逐次予約・再開。
- **各ブラウザー1,008,000 PCM値のレーン別結果と、一定順で足した合成結果が完全一致（誤差0）**。

Chromeのネイティブミキサーの別context間比較は最大`2.9802322387695312e-8`（約−150.5dBFS）の差がありました。旧実装同士の対照でも同じ最大差が出ています。各レーンの入力PCMと固定順合算がbit一致し、旧/旧でも差が再現することから、ネイティブミキサーの加算順によるFloat32丸め差と判断します。この非決定性を隠して「全ネイティブ合成bit一致」とは報告しません。WebKitのネイティブ合成は今回の旧/新・旧/旧とも誤差0でした。最適化による誤差の無条件許容値は導入していません。
