# Phase 1b / B2 音量エンベロープの形状保持

> 開発時点の記録です。2.2.84の最新の採否・制約・公開状態は[リリース報告](PVE-2.2.84-RELEASE-REPORT.md)を参照してください。


2026-10-23、2.2.83作業ツリーの未公開修正。B1・既存未公開差分を保持し、バージョン更新・公開は行っていません。

## 1. 原因

再生評価はhold終端の直前に`min(5ms, 区間長/2)`のdB線形ランプを設けます。一方、旧split/trimは`stepRamp=0`で境界値を採取し、編集後は短縮した区間からランプ幅を再計算していました。境界値だけ合わせても、開始点の消失・半区間制限によってランプが移動します。境界1µs以内の点を除外/統合する処理も近傍の形状を失わせていました。

## 2. 修正・変更ファイル

- `dist/clip-envelope.js`：`splitEnvelope` / `trimEnvelope`を共通の区間切出しへ接続。境界値は再生と同じ式で評価し、切断されたholdの残りランプ幅を`holdRampSeconds`へ保持します。`envelopeDbAt`と専用の区間評価関数がこの幅を使用します。従来の5msランプの意味は未編集データで維持します。
- `normalizeEnvelope`：上記の任意属性と`editBoundary:true`を保持。編集境界の隣だけは正の微小間隔を残し、1ns/1ps前後の点を統合しません。通常点の従来の重複除去と256点制限は維持します。点の属性配置を揃え、未使用属性は`undefined`としてJSONには出しません。
- `remapEnvelope`：連動音声のtrim経路も、元時刻との写像が変わらない切出しに限り同じtrimへ接続。速度変更時の既存の点移動処理は維持し、Speedエンジンは変更していません。
- `engine/core.py:gain_envelope_expression`：新しいランプ幅を解釈。編集境界を含む式だけ17桁の精度で出力し、旧データの式は従来の文字列を維持します。音声処理全体の作り直しはしていません。
- 回帰試験：`tests/envelope-edit-safety.test.mjs`（既存`clip-gain-envelope.test.mjs`から実行）、`tests/envelope-edit-native.test.py`、`tests/fixtures/envelope-edit-cases.mjs`、独立した旧評価オラクル`envelope-pre-b2.mjs`。
- 証拠生成：`scripts/check-envelope-edit-safety.mjs`、実ブラウザ検証：`scripts/check-envelope-edit-browser.mjs`。ROADMAP/UXと作業stateも更新しました。

**構造変更の理由**：既存のhold表現だけでは、短縮区間でも元のランプ開始地点を保持できません。開始点を補助ポイントとして追加する方式は採用せず、点数を増やさない任意属性を選びました。トップレベルの保存versionは変更しません。旧プロジェクトは従来どおり読み取ります。ただし、新属性を含む編集結果を旧版で再保存すると形状情報が失われます。旧版への逆保存は保証せず、実利用時は編集前のプロジェクトを別名で退避してください。今回、ユーザーの保存済みプロジェクト・素材には触れていません。

## 3. 数値比較と精度

旧不具合の調査スクリプトは履歴として変更せず、B1修正済みで全体を通せないためB2部分を単独で修正前コードに対して実行しました。修正前再現（開発監査資料・配布対象外）。不具合が出ることを期待する調査と、正しい結果をassertする回帰試験を分けています。

8系統・146切出しについて、全区間の高密度サンプルとランプ開始/終端・切断位置周辺を比較。hold前/中/後、5ms内、連続点、上昇/下降、4µsクリップ、1ns/1ps近傍、左右接続、trim、反復編集を含みます。時刻は編集前クリップ内の座標です。モデル試験では一定速度/既存可変速度とも元映像時刻への対応を介して比較しています。

| 比較 | 修正前 | 修正後 |
|---|---:|---:|
| 既報：0.998秒でsplit、右先頭 | -12 dB（元は-4.8 dB） | -4.8 dB |
| 既報：0.997秒の左/trim側 | -12 dB（元は-7.2 dB） | -7.2 dB |
| 同条件1,488,034点の最大dB誤差 | 81 dB | 7.8515×10⁻¹³ dB |
| 最大dB誤差の位置 | mixed点列のtrim [0.003,0.008]、元0.0035秒 | 先頭/末尾定数区間を含むsplit-right [0.199999999,2]、元1.199999秒 |
| 最大線形gain誤差 | 全結果参照（開発監査資料・配布対象外） | 1.8030×10⁻¹³ |

主試験の許容値は測定前に **1×10⁻⁸ dB / gain 5×10⁻⁹** と定義し、変更していません。未編集の旧評価160,008点はdouble値で完全一致しました。

**長い絶対座標は別集計**です。1200秒付近は最大2.6193×10⁻¹⁰ dB（元1201秒）、24時間上限付近は最大1.1176×10⁻⁸ dB（元86399秒）。後者は主試験の1×10⁻⁸ dBを僅かに超えます。旧式を変更せずに座標を引き直す際のdouble丸めとして、追加試験では`8 × Number.EPSILON × 最大座標 × 最大勾配`を別の丸め予算としています。この例の予算はそれぞれ5.1244×10⁻⁹ / 3.6835×10⁻⁷ dBです。主試験の基準を緩めて隠してはいません。位置を含む数値結果（開発監査資料・配布対象外）に記録しました。

## 4. PCM比較と残る音声差

| 実処理 | 比較条件 | 結果 |
|---|---|---|
| ブラウザ書き出し側の実`mixWindow/gainAtCompiled` | 48kHz・ステレオ合成波、8分割位置、同じ元サンプルに同じ音量を適用 | 修正前は最大0.1253045、修正後のエンベロープ由来差は0（許容1×10⁻⁷） |
| Chrome/WebKit `OfflineAudioContext` + 実`AudioPreview.scheduleGain` | 各5分割位置。元カーブを同じスケジュール位置へ評価した参照との比較。既存declickを双方同条件で適用 | 修正前は最大約0.02710、修正後は両ブラウザとも0（許容1×10⁻⁷）。生成曲線ごと1回のcompileを確認 |
| 実FFmpeg | サンプル単位の式と、既存の64sample volume処理。264ケース・6,227,896 mono samples、元時刻へ戻した参照と同じ処理グリッドで比較 | PCM最大差0（許容2×10⁻⁷）。旧データ78式の文字列も旧実装と一致 |

**未分割の生PCMと分割後の生PCMは完全一致しません。** 既存のクリップ端8msのクリック抑制は残しています。JS実ミキサーの生比較は最大0.2804193で、今回の8位置では境界±8ms外の差は0です。FFmpegの0.998秒分割では、フェードなしでも64sample処理グリッドの位相差により最大0.0420591（元1.000645833秒）、既存フェード込みで最大0.1980148（元1秒）の差が残りました。

これは既存DSPの仕様による差で、技術的に不可避という意味ではありません。今回、これらをエンベロープの許容誤差へ混ぜたり、音声エンジンを変更して消したりしていません。「分割しても生PCMの音量が一切変わらない」という全体仕様まで達成したとは報告しません。

証拠：JS PCM（開発監査資料・配布対象外）、Chrome/WebKit（開発監査資料・配布対象外）、FFmpeg・生連結差も記録（開発監査資料・配布対象外）。

## 5. Undo/Redo・保存復元

モデルのsnapshot/JSON→sanitize、反復split/trim、連動音声のsplit/trimを検証しました。連動音声では既存4種類の可変速度曲線×3切断位置も追加し、元映像時刻で120,012点、最大2.7889×10⁻¹³ dBでした。加えて、独立したChrome/WebKitで実アプリの分割ボタン、IN数値入力、Undo/Redo、保存ダイアログからの`.project`ダウンロード、実ファイル入力での再読込を操作しました。新属性とカーブが保持され、trim後先頭は-4.8 dBでした。合成プロジェクトだけを使用しています。

## 6. 性能・既存最適化

`mobile-model.js`の事前compile/gain評価、`audio-preview.js`のスケジューラーはファイルhash不変です。サンプルごとのfilter/map/sortを復活させず、永続キャッシュも追加しません。今回の正規化と同一写像判定は編集時の処理です。

## 8. 未検証・保証外

実機iPhone/Safari・実聴・長時間連続再生・フル映像書き出し・エンコード後の聴感は未検証です。FFmpeg試験は音量式と音声フィルターの実行であり、全Mac/HTTP/パッケージ回帰ではありません。任意の同時速度変更後のカーブ設計、既存の8ms処理、ネイティブ64sample処理の品質改善は今回の対象外です。旧版への逆保存と、次項の点数上限も保証対象から分けます。

## 9. B3への影響

MAX=256と先頭からのslice、`addEnvelopePoint`の上限処理は変更していません。ランプ開始用の補助ポイントは追加しません。旧dense再現と修正後はともにtrim末端0.992217899秒（期待1秒）、split末端0.996108949秒（期待0.999秒）であり、B3は未修正です。独立したB3診断（開発監査資料・配布対象外）。

したがって、端点の追加により256点を超える入力ではB3によって形状を失い得ます。これはB2解決済みとして扱いません。また、B2では微小距離の編集境界を保持するため、従来なら統合された点が残る場合があります。B3では境界点と`holdRampSeconds/editBoundary`を保持し、黙った切捨てをなくす必要があります。

## 10. 採用判断・次作業

**B2の曲線保持修正は採用を推奨し、B3へ移行可能です。** 点数上限に達しない検証条件では形状保持・往復編集・両経路の評価が成立しています。長座標の丸め予算、新属性の旧版逆保存制約、既存DSPによる生PCM差は上記のとおり残ります。

ただし、無条件の納品品質保証や公開承認ではありません。B3を別作業で解消し、正式公開前に既定の全Python/HTTP・Macパッケージ・実機/聴感の必要な検証を行ってください。8ms処理/64sampleグリッドの品質方針は、B3と混ぜず別課題として判断できる状態です。
