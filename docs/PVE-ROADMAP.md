## Phase 1a：B1の実装チケット（実装済・未公開）

結果・保証範囲・検証は[B1安全性修正](PVE-B1-STORAGE-SAFETY.md)を参照します。Phase 1aの時点ではB1のみ変更しました。現在はB2・B3・B4も別作業で検証済みです。統合公開は未実施です。

**目的**：同じ素材ID・同名ファイルの再コピー失敗で、保存済み素材コピーを削除しない。

- 対象：`dist/project-storage.js:copyMediaToProject` / `writeFile`、`tests/project-storage.test.mjs`と必要な呼出元。保存方式の全面刷新、UI移動、B2〜B4は含めません。
- 現状：`getFileHandle(create:true)`は既存も返し、書込失敗後に無条件`removeEntry`。模擬writerで既存コピー削除を再現済みです。
- 先に決めること：既存/新規の識別、書込開始前・write・closeの各失敗後の保証、並行再試行の所有権。既存判定だけで途中上書きの安全性まで保証したことにはしません。
- 実装案：既存コピーを直接削除しない。必要なら一時名への書込完了後に参照を切り替える等、対象APIで確かめられる安全な方式を選びます。参照の確定と旧コピー整理を分離します。
- 受入：既存/新規×getFileHandle/createWritable/write/closeの失敗、abort失敗、同ID再試行/競合を注入。既存内容と参照を保持し、再読込と再保存が成功することを確認します。名前/参照形式変更が必要なら影響説明・バックアップ/移行を先に用意します。
- 検証：保存局所試験→Chrome実File System Access APIで使い捨てフォルダ確認→全JS/build。Mac保存経路にも変更が及ぶ場合は対応するPython/HTTP検証を追加。公開は別の明示された作業です。

## Speed統合：今回の設計調査

**現行の事実**：`model.js:speedAt/computeTiming`は一定速度または始点/終点速度とカーブを扱い、可変速度は元映像区間を32分割して時間積分を近似します。`timingBase`で分割/trim前のカーブを参照し、`sourceOffset/outputOffset`で双方向変換します。`mobile-model.js:sourceTime`、タイムライン、音声、Mac側処理が関連し、音量の`remapEnvelope`は元映像時間に点を追従させます。任意点カーブ・タイミングアンカー・ビート拘束はこのモデルにはありません。

**提案する契約**：Speedを一つの設定系として、一定速度・複数点カーブ・滑らかな加減速・タイミングアンカーを扱います。クリップ内の出力時刻`t`と元映像時刻`s`の単調写像`s(t)`、逆写像、速度`ds/dt`を一組として定義し、プレビュー/音声/出力が共用します。元映像基準で速度を定義する方式との違いも試作で比較し、保存形式決定前に選びます。

| 設計項目 | 決める内容・受入例 |
|---|---|
| 多点カーブ | 点の時間軸、補間方式、最小/最大速度、連続性、積分/逆変換の誤差。曲線の見た目と実際の速度が対応する |
| アンカー | 「元の特定フレームsを出力tへ置く」を明示。2点以上の拘束時、曲線/尺のどちらが変わるか表示。順序逆転/実現不能は黙って補正せず理由を示す |
| ビート同期 | 音楽マーカーを出力軸の目標として利用。自動解析は補助。選択フレームを選択ビートへ合わせ、音楽自体の時刻を不用意に変更しない |
| 尺の所有権 | 「速度変更で長さが変わる」と「長さ固定で曲線を再配分」を明示。後続クリップ/overlayを動かすかは別の編集モードとして定義 |
| split/trim/静止 | 元フレームとアンカーを保ち、分割後の写像を再フィットしない。freeze/holdの非可逆区間は単調可逆部と区別して扱う |
| 音声 | 連動/独立、原音の速度追従、ピッチ保持の必要範囲、音量点の基準、seek後の同期を契約化 |
| 保存/移行 | 旧speed/endSpeed/curve/timingBaseを読み取る変換案、版管理、別名保存、ロールバック。破壊的変更前に説明 |

**技術的推測**：現行32分割をそのまま増やすだけでは、多点拘束とビートへの正確な対応、固定尺の競合解決を一貫して表現しにくいと考えられます。新エンジンが必要か、既存写像の拡張で足りるかは未決定です。次の設計作業では数値fixtureと操作モックで比較し、エンジン実装とは分けます。

## 手ぶれ補正：独立研究の入口

**事実**：ブラウザは`mobile-stabilize.js`の低解像度輝度パッチによる移動/小回転推定と経路平滑化を、プレビューと出力で共有しています。既定解析サイズ72、サンプル数は既定18fps・上限18,000。デコード/取消は呼出側が所有し、結果は速度変換前の素材時間に対応します。Macのvidstabは別方式です。実用品質が不足するという評価はユーザーからのものです。今回の実写比較で原因を特定したわけではありません。

**推測**：低解像度・前景の動き・追跡外れ・パララックス・時間サンプリングなどが品質の制約になり得ます。各要因を切り分ける必要があります。

**研究案**：現行を比較基準にし、特徴点追跡＋外れ値除去＋相似/アフィン推定、領域/フローに基づく推定、平滑化/クロップ方針の別候補を比較します。これらは未評価の候補で、採用・ブラウザ性能・実装ライブラリは未決定です。WebGPU前提にしません。

研究用アダプターの案は「デコード済みフレーム＋素材timestamp＋設定＋取消」→「素材時間別変換＋信頼度＋クロップ情報＋方式/設定/素材識別子」です。デコーダーと推定器を分離し、同じフレーム列を候補へ渡し、既存レンダラーには採用後の別作業で接続します。研究結果は本番保存へ無断で混入させません。Labは隔離実験に利用できますが、そのまま本番へ転記しません。

比較素材：静止背景の手持ち、意図的パン、歩行、低照度/低模様、動く前景、パララックス、縦横動画。残留揺れ・不自然な変形・パン保持・画角/クロップ・失敗率を同じ画面で評価し、解析秒/素材秒・ピークメモリ・プレビュー/出力の変換一致も測定します。ローリングシャッター/被写体変形の解決を保証しません。M2 MacとiPhone 16 Pro/Safariの実写・実機評価後にのみ採否を決めます。

## 検証・コンテキストの運用

- 毎回stateとgit statusから再開し、対象のコード・試験・文書だけを読む。過去ログ全文を読み直さない。公開版と未公開差分を区別する。

- 正式公開前は全JS、Python実動画/音声/HTTP、Macパッケージ、影響経路の実ブラウザ確認。未確認の実機/実聴/長時間を明記する。

- 文書更新と実装変更は分け、公開・バージョン更新は明示依頼時のみ行う。
